1结论

这个项目在 3 小时 13 分钟内完成了 5 次提交，演化路径极其清晰，是一次典型的"能力先立起来、再被现实打脸、再回头修正"的三段式：

text
阶段 A（02:53）  功能骨架：一次性脚本抽象成可安装包
阶段 B（03:08）  协议重写：主协议与 sync 子协议分帧混用 → 按 AOSP 重写
阶段 C（03:56）  真机校准：抓包逐字节比对，4 处偏差全部修正
阶段 D（04:06）  知识沉淀：把抓包结论写成文档
阶段 E（04:2x）  体验补齐：hosts 分组 + PR 模板 + 徽章

最值得注意的一点：阶段 C 的 4 处偏差，没有一处能靠读文档发现。AUTH 签名格式、CNXN 版本号、shell v2 长度字节序，全部与 AOSP 文档的表述有出入，只能靠中间人代理抓官方 adb 的真实报文来定位。这构成了本项目最核心的一条演化规律：协议层的正确性不来自文档，而来自与参照实现逐字节对比。

而阶段 E 是一次典型的领域需求反向驱动基础层——"路由器 hosts 要分批生效"这个外部约束，逼出了 profiles.Profile.host_groups() 这个基础层方法。

3二、阶段划分

阶段 A · 功能骨架（1c9ad54，02:53）

做了什么：一次性 PowerShell 脚本抽象为可安装的 Python 包。

关键结构决策在这一次就定下来了，后续没有推翻：

决策体现是否被后续推翻
零第三方依赖pyproject.toml dependencies = []❌ 未推翻，一直保持

这个阶段的判断力：在还没有遇到任何真机问题之前，就把"可逆性"和"防注入"写成了硬约束。这两条后来一次都没有成为 bug 源头。

阶段 B · 协议重写（b46239c，03:08）—— 决定性重构

触发：初版 ADB 客户端"shell 能通但 pull 会超时"。

根因：初版把 adb 主协议和 sync 子协议的分帧混在一起。sync 子协议是 8 字节 ASCII 头（RECV/DATA/DONE），主协议是 24 字节小端二进制头，两者混用必然在某个方向上错位。

逐文件分析：

文件变更语义移动
mitvclean/adb.py+365 −约 200协议实现整体重写：握手从错用 SYNC 改为 CNNX；magic 校验从固定值改为 command ^ 0xFFFFFFFF；shell 输出走主协议 WRTE 分帧；pull 单独走 sync 子协议；新增 AUTH 流程
tests/test_adb_protocol.py+251（新建）验证策略诞生：不再依赖真机，改用"假 adbd"（一个本地 socket 服务端模拟设备）验证握手/开流/读写/认证
mitvclean.bat+57（新建）分发形态：Windows 双击即用
README.md+22文档同步
.github/workflows/test.yml±5CI 接入新测试

这次重构最重要的产物不是代码，是测试策略。 tests/test_adb_protocol.py 里的 FakeAdbd（test_adb_protocol.py:28-145）是一个完整实现了 CNXN/AUTH/OKAY/WRTE/CLSE 的假设备端。此后所有协议调试都不需要真机在场。

代价：adb.py 从约 340 行涨到 513 行，一次性把协议层推到全项目最大单体。

阶段 C · 真机校准（debe01a，03:56）—— 与参照实现逐字节对齐

触发：电视开启 ADB 后连不上。

方法（提交信息里写明）：用中间人代理抓官方 adb 与真机 adbd 的双向报文，逐字节比对。

4 处偏差：

#偏差文档说法实测真相位置
1AUTH 签名标准 PKCS#1 v1.5 套 SHA-1 摘要00 01 FF..FF 00 ‖ SHA1_DigestInfo(15B) ‖ 原始 token —— 末尾放 token 本身，不是摘要adb.py:102-126 _rsa_sign

4shell v2 分帧长度字段按常规大端读小端；按大端读会得到 83886080adb.py:433-456 _parse_shell_v2_chunk

外加一条设备特性发现：小米 adbd 在同一连接上连续开第二个流会被 CLSE 拒绝，官方 adb 也是每命令一条连接。应对方式是把重试下沉到协议层：

python
# adb.py:392-404
def run(self, command: str, read_timeout: float = 60.0) -> str:
    """执行一条命令，失败时自动用新连接重试一次。"""
    try:
        return self.shell(command, read_timeout)
    except AdbError:
        self.close()
        self.connect()
        return self.shell(command, read_timeout)

这是本项目最漂亮的一次设计：设备 quirk 没有泄漏到任何调用方。cli.py 里 20 多处 dev.run(...) 一行都不用知道这件事。领域层与设备实现之间保持了干净边界。

附带发现：ads.py/cli.py/packages.py 也跟着改了 40 多行——是 dev.run() 的调用方式从"直接 dev.shell()"改成"统一走 dev.run()"的接口收敛，属阶段 C 的余波。

阶段 D · 知识沉淀（d67e9e0，04:06）

做了什么：把阶段 B/C 的踩坑写进 docs/ADB协议实现笔记.md（129 行）。

为什么这一步重要：协议结论是"只有这台电视、这个固件验证过"的。把它们写进文档并明确标注来源（抓包实测），后来者可以：

  • 直接复用结论，不用重走 3 小时弯路
  • 知道哪些是实测的、哪些是文档说的

文档里明确纠正了网上的错误说法："AOSP 常量 A_VERSION 是 0x01000000，但官方 adb 实际发的是 0x01000001"。

阶段 E · 领域需求反向驱动基础层（b277c37，04:2x）

触发需求（来自真实使用反馈）：73 条 hosts 一次性贴到路由器，第 2 组是内容源域，拦了会让对应 App 打不开。必须分批生效。

驱动的抽象下沉：

这是"领域需求反向驱动基础层"的完整证据链：一个纯外部的使用约束（路由器 UI 只能整块粘贴且有副作用），一路穿透到最基础的数据层解析规则，中间没有任何一层"顺手"妥协。

同时补齐了开源协作设施：PR 模板、两个 Issue 模板（bug / 机型画像）、README 徽章、CONTRIBUTING 的"三种参与方式"。这是从"单人脚本"到"可接受外部 PR 的项目"的转变。

5四、演化中的两次"决定性重构"

决定性重构一：b46239c · 主协议与子协议分离

为什么是决定性的：它同时改变了两件事——协议实现的正确性，和整个项目的测试策略。在此之前，验证 ADB 客户端只有一条路：连真机。在此之后，协议层有了确定性回归测试。

抽象下沉轨迹：

text
设备 quirk（同一连接不能连开两个流）
    ↓ 泄漏到协议层
AdbDevice.run() 的换连接重试        adb.py:392-404
    ↓
领域层完全无感（cli.py 里 20+ 处 run() 调用零改动）

泛化方式：run() 不是为某一个命令写的补丁，而是把"重试 + 换连接"变成协议层的通用契约。这让任何未来新增的命令都自动获得这个容错。

决定性重构二：debe01a · 与参照实现对齐

为什么是决定性的：它揭示了一个方法论层面的事实——协议层的正确性无法靠阅读文档获得。AOSP 文档在 AUTH 签名格式、CNXN 版本号这两点上都会把人带偏。

这次重构的产物是方法论，被写进 docs/ADB协议实现笔记.md 的开头：

"网上流传的很多说法是错的。"<br>"对照 adb devices 的官方行为和 AOSP 文档，能定位到 4 处偏差。"

同时它逼出了一个工程纪律：所有协议相关的结论都必须标注来源是"文档"还是"抓包实测"。这条纪律让 docs/ 里三篇文档的可信度分层清晰。

7六、结论

演化史给出的判断是：这个项目的架构骨架一次成型且方向正确（阶段 A 的四个决策全部存活），之后的四次提交都是"现实问题 → 局部修正"的正确模式，没有出现"推翻重来"。

真正的风险不在架构，在演化速度远快于验证沉淀——3 小时 13 分钟 5 次提交，其中 3 次是协议层的紧急修正。这意味着：

  1. 阶段 C 的 4 处偏差是在一台电视、一个固件上验证的，其他型号/其他固件的 adbd 行为可能不同
  2. 那些"抓包结论"目前只在文档里，没有固化成自动化测试（假 adbd 模拟的是我们以为的 adbd，不是真实的）
  3. ruff 的 49 条告警说明静态检查从未进入过开发闭环

建议的下一步（详见《mitvclean 代码质量评估》P0/P1）：

  • 把 ruff check 加进 CI（成本几乎为零，立刻暴露 49 条中真正值得修的那些）
  • 把 adswitch 纳入可逆闭环，补上项目自己声明的那条不变量
  • 在 docs/ADB协议实现笔记.md 里给每条结论标注"适用固件范围"，避免后来者误以为全机型通用
