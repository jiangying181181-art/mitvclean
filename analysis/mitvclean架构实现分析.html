1结论

这是一个四层单向依赖的极小工具型项目：协议层（adb.py）→ 领域层（packages.py / ads.py / profiles.py）→ 应用层（cli.py）→ 数据层（profiles/ 目录 + work/ 运行时产物）。

它的架构判断力体现在三处，而不是文件数量：

  1. 依赖方向严格单向，零反向引用。 领域层只 from .adb import AdbDevice 拿一个连接对象，从不反向引用 CLI；CLI 是唯一知道"用户想干什么"的地方。这让 packages.py / ads.py 可以在完全离线的条件下被测试（tests/test_offline.py 里的 FakeDevice 就是这么替身掉 AdbDevice 的）。
  2. 数据与代码分离是硬约束，不是口号。 机型画像放在仓库根的 profiles/<slug>/，profiles.py 里没有一行针对具体机型的 if。加新机型 = 复制目录改内容，零代码改动。
  3. "可逆"这个领域概念只在一处定义，贯穿到底。 状态快照（save_record）→ 按快照还原（enable_packages）→ 测试对称性验证（test_restore_only_reenables_what_was_enabled）。这是整个项目最核心的业务不变量。

代价也很明确：应用层 cli.py 的 cmd_doctor 圈复杂度 17（radon 实测，C 级），是唯一越过"命令层只做编排"边界的函数；cli.py 覆盖率仅 18%，是全项目最薄的测试防线。

分层成立的证据

检查项结果证据
领域层是否引用应用层❌ 无packages.py / ads.py / profiles.py 的 import 只有 from .adb import AdbDevice 与标准库
协议层是否引用领域层❌ 无adb.py 只 import 标准库（base64/hashlib/os/socket/struct/subprocess/sys/pathlib）
协议层是否含业务判断❌ 无adb.py 中唯一的"策略"是 run() 的换连接重试（adb.py:392-404），是传输层容错
应用层是否绕过领域层直接操作设备⚠️ 部分cli.py 直接调 dev.run(...) 取系统属性（cli.py:63-64, 93-98, 134-135）——只读探测，可接受
领域层是否依赖具体机型❌ 无profiles.py 全文无机型字符串；机型信息只从 profile.json 读

唯一的越界点：ads.py:191-214 的 find_ad_settings 内嵌了"哪些 settings 键算广告键"的关键词表（("ad","splash","boot","front","skip","vip")）与排除词表（("bluetooth","keyboard","alarm",...)）。这是业务知识被写死在协议无关的领域层里——但它只影响"哪些键被读出来给人看"，不影响任何写操作，风险可控。

3二、层间结合机制

本项目没有框架，用的是三种朴素机制：

机制实现位置
数据驱动注册目录即注册表：profiles/ 下每个含 profile.json 的目录自动成为一个可用画像profiles.py:97-104 list_profiles() 遍历 PROFILES_DIR.iterdir()
装饰器式状态捕获with _connect(args) as dev: 打开连接、退出时关闭cli.py:91, 133, 187, 294, 327, 349, 372 全部走 AdbDevice.__enter__/__exit__（adb.py:301-306）
异常 → 退出码映射ProfileError → 2、AdbError → 3、KeyboardInterrupt → 130cli.py:455-464 main() 的 except 链

校验体系（分四层，每层守不同东西）：

层校验守什么位置
1. 输入格式包名必须匹配 ^[A-Za-z_][A-Za-z0-9_]*(\.[A-Za-z0-9_]+)+$防清单注入（清单内容被当 shell 片段执行）packages.py:23, 60-65
2. 输入内容清单为空直接抛错；非法行报"文件:行号"防空操作与静默错误packages.py:96-103
3. 状态前置只禁用 STATE_ENABLED 的包不动用户自己关掉的东西packages.py:173-175
4. 持久化完整性先写 .tmp 再 Path.replace() 原子替换断电/中断不留半截记录packages.py:141-143

四层校验的顺序不可交换：第 1 层必须在第 3 层之前——如果先把未校验的包名拼进 pm disable-user --user 0 {n}，注入就已经发生了。

5四、架构优势

#优势证据代价
1零第三方依赖使领域层天然可测pyproject.toml dependencies = []；tests/test_offline.py 用 FakeDevice 在无网络下跑完 17 项无依赖也意味着没有成熟的 RSA 库，ADBP 密钥解析得自己写（adb.py:151-184），是 100 行手写 DER 解析
2数据与代码分离让适配成本趋零profiles.py 无机型特判；CONTRIBUTING.md 明确"不需要改任何代码"画像文件的 schema 无强校验（profile.json 写错字段名只会静默取默认值，见 profiles.py:41-57）
3"可逆"作为领域不变量只定义一次save_record / enable_packages / 对称性测试三处呼应快照只记录包状态，不记录 settings 开关原值——adswitch --set 改了广告开关后无法自动还原
4协议层是唯一不透明处adb.py 集中承载全部抓包结论，其他层完全不知道自己走的是 ADB协议层 513 行占全项目 31%，是最大的一块单体

6五、架构代价

#代价具体位置影响
1CLI 层承担了本该属于领域层的编排判断cli.py:131-178 cmd_doctor 圈复杂度 17（radon C 级），内部混合了"读广告设置 / 查包状态 / 列缓存目录"三种关注点难以单测；cli.py 覆盖率仅 18%，出问题难定位
2运行时状态与版本化数据混在同一 work/ 目录快照、hosts 产物、logcat 全落 work/快照文件没有过期清理机制，跑多了会堆积；restore 自动取"最新"的 state-*.json（cli.py:367-370），在多机型/多次操作场景下可能取错
3adswitch 写操作无对称还原ads.py:217-228 set_ad_settings 只写不存原值用户设了 4 个开关后无法一键回退，与项目"只做可逆操作"的整体承诺不一致
4协议层单文件过大adb.py 513 行 = 密钥管理 + 帧编解码 + 三种流协议 + 业务重试任何协议改动都集中在这一个文件；但 CC 最高仅 8，说明是"长而浅"而非"深而复杂"
—

7六、结论

架构本身是健康的：四层单向、零反向引用、协议隔离良好、数据驱动适配。对一个 2 千行的工具来说，这个结构已经优于同类开源项目（cleanyourtv / MiTVNoAd 都是脚本形态，无领域/协议分层）。

真正需要动的是三处具体位置，而不是重构架构：

  1. cli.py:131 cmd_doctor 拆成三个小函数（CC 17 → 各 < 8）
  2. ads.py:217 set_ad_settings 加原值快照，补上"可逆"闭环
  3. profiles.py:41-57 Profile 的 meta 读取加未知字段告警，避免画像写错静默失效
